# Mercury host 0.2.4

A patch release. Two host-side fixes protect operator trust in what the host says about itself — a
migration that claimed a version whose objects were missing, and a credential profile that accepted an
owner id no Run could ever match. The release pipeline learns to say when a channel was not updated,
and the nightly skill stops being blind: it checks the model before it claims, names the Runs that
failed, and files proposals again.

## Install

```bash
npm install -g @aywengo/mercury        # 0.2.4
```

Or:

```bash
git clone https://github.com/aywengo/mercury.git
cd mercury
npm ci
```

Or from Homebrew (formula `mercury-ai`; homebrew-core owns `mercury`, the Mercury language compiler):

```bash
brew tap aywengo/mercury https://github.com/aywengo/mercury
brew install mercury-ai
```

Requires Node.js >= 22.18 and `git`. `mercury --version` prints `mercury-host 0.2.4`; `GET /healthz`
reports `"version": "0.2.4"`.

## Migrations verify the schema, not the version number (#1032, PR #1034)

`mercury migrate` recorded a version as applied and never looked at the objects it was supposed to
create. A database whose `schema_migrations` claimed a version while a table was missing kept starting,
and every Run creation then returned 500. The verifier now compares `sqlite_master` and
`PRAGMA table_info` against the expected schema and reports the drift.

## `credentials validate` refuses an owner id that can never match (#1035, PR #1038)

A credential profile accepted a placeholder owner id, and the profile then refused every Run the bot
created — a configuration error that looked like a worker failure. Validation now rejects an owner id
that cannot match the identity it is meant to bind.

## Credential profiles may inject the two nightly gate variables (#1010, PR #1049)

A profile's `env` refused every `MERCURY_*` name, which is right for host configuration
(`MERCURY_DB`, `MERCURY_API_TOKENS`, `MERCURY_ADMIN_TOKEN`) and wrong for the two names the nightly
skill needs to read the host API. `MERCURY_API_URL` and `MERCURY_API_TOKEN` are now the only
exceptions; nothing in `src/` reads either, and the refusal message names them.

## The release pipeline says when a channel was not updated

- The Homebrew formula is pushed with the operator identity, and when the push is refused the job
  **corrects the published release body** before failing, instead of leaving a page that tells readers
  to install a version Homebrew does not serve (#1029, PR #1046).
- A probe that never answered is reported as `HTTP 000`, not `HTTP 000000` (#1045, PR #1047).
- The npm channel state in the notes is read from the registry rather than inferred from the verb the
  job ran (#994, PR #1017).

## Nightly skill

- **The model endpoint is checked before the ladder claims** (#1040, PR #1041). A crashed model server
  used to cost an issue and 17 failed Runs; now the Run stops before claiming, with a record.
- **The morning report lists the Runs that failed** (#1042, PR #1043). A failed Run opens no PR and
  posts no comment, so every other section read `_none_` and a lost night looked quiet.
- **Rung 4 files proposals again** (#1018, PR #1048). The dedupe walk capped at 10 pages of an endpoint
  that returns issues *and* pull requests; the repository outgrew it and the fail-closed rule made the
  rung a permanent no-op. Dedupe now asks the search API.
- **The rung-1 e2e gate reports its state** (#1010, PR #1049): `configured`, `absent`,
  `half-configured` or `unevaluable`, so "passed" and "never checked" stop being the same value.

## The CLI

`mercuryctl`, the operator client, ships inside this same package — there is no separate CLI artifact
and no CLI-only channel. Both binaries arrive with any install:

```bash
mercuryctl --version                    # 0.2.4
mercuryctl runs show <runId>            # timeline, events, workspace pointer
```

The CLI talks to the same owner-scoped API the dashboard uses; every endpoint it calls is documented
in [`docs/api.md`](../../api.md).
