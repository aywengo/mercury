# Mercury host 0.2.1

Patch release carrying the accumulated fixes from the first two weeks of the nightly self-development
loop, plus the first credential-profiles slice. The headline fix is for the nightly host itself:
**a Run whose agent dies on a provider error is now FAILED, not silently COMPLETED.**

## Install

```bash
npm install -g @aywengo/mercury        # 0.2.1
```

Or:

```bash
git clone https://github.com/aywengo/mercury.git
cd mercury
npm ci
```

Or from Homebrew (formula `mercury-ai`; homebrew-core owns `mercury`, the Mercury language
compiler):

```bash
brew tap aywengo/mercury https://github.com/aywengo/mercury
brew install mercury-ai
```

Requires Node.js >= 22.18 and `git`. `mercury --version` prints `mercury-host 0.2.1`; `GET /healthz`
reports `"version": "0.2.1"`.

## The headline: silent-green nights are over

On the night of 2026-09-30 the nightly host's model server was down from 19:42 to noon the next day.
All 17 nightly Runs fired on schedule and were recorded **COMPLETED in ~1.3 s with zero output** — the
RPC supervisor delivered `agent_end` after the provider failed, and the adapter settled exit 0. The
morning digest never fired, nothing was claimed, and Mercury showed a green night.

The PrimeAgent adapter now tracks whether the session produced any substantive Mercury event —
assistant text (excluding exactly the four synthetic `[agent] …` status lines the translator emits for
compaction/auto-retry frames), a tool execution, an input dialog, or a goal report — and on `agent_end`
with code 0 but no substance settles a failure (`code 1`, `errorKind 'agent'`) whose message carries the
provider's own error from `agent_end.messages[*].errorMessage` (the worker redacts before persisting).
`start()` and `resume()` share one event handler; the per-turn flag resets on resume. The worker records
FAILED, so an outage reaches the morning digest instead of a green nothing (#803, #804).

## Credential profiles CP-2 (#784, #799)

The first slice of the [credential-profiles design](../../../docs/credential-profiles-design.md):
the profile file schema at `${XDG_CONFIG_HOME}/mercury/credential-profiles.json` (mode 0600 gate like
bot credentials), repository-id normalization, and a strict loader that never prints values. Validate
from the CLI:

```bash
mercury host credentials validate
```

`ok`/`FAIL` lines per profile, exit 1 on any FAIL. Malformed JSON, `git.httpsToken` and
repository-entry errors are value-free; userinfo in repository URLs is redacted (`[REDACTED]`),
including username-only credentials. Unknown fields are refused with a did-you-mean suggestion, the
owner-wide `*` is only accepted as the last segment, and the env dictionary is null-prototype so
inherited keys (`toString`) can never satisfy the `git.httpsToken` cross-check.

## Nightly loop: features, stale-claim reset, room to work (#800, #801)

- **Feature rung.** The ladder gains a rung 2: `enhancement` issues authored by @aywengo, or carrying
  a current `enhancement` label applied by @aywengo (the same timeline-actor provenance rule as
  `nightly:ready`, #764), ordered by priority label then age, and run through the issue-fix-loop like
  any other fix. Old rungs renumber: new unlabeled issues → 3, docs → proposals → 4.
- **Stale-claim reset.** `docs/nightly-self-development.md` §4.3 always promised "the next night
  resets it" — now it happens: an `nightly:in-progress` claim whose label event predates the current
  night's local midnight is removed before selection, so a deadline-stopped Run no longer blocks its
  issue forever. A claim from tonight still excludes (a live Run holds it); `--dry-run` writes nothing;
  a failed reset fails closed for that issue only. Claim ownership is verified through the label
  timeline's final actor — GitHub's add-labels is idempotent, so the previously assumed
  422-already-exists race signal never fires.
- **Feature-sized room.** The `nightly-next` example task's cap goes 80 min → 4 h (`notAfterAt` 06:00
  still bounds every Run at the window edge) and its skills list grows to `issue-fix-loop`, `planning`,
  `implementation`, `testing`.

## Other fixes

- **Worktree from `localPath` (#791).** A workspace whose repository context points at a local path is
  built from it, not re-cloned from the URL — removes a long-standing nightly flake (#596).
- **Nightly e2e self-installs dependencies (#796).** A clean worktree without `node_modules` no longer
  files spurious module-load-failure issues; the e2e skill runs `npm ci` when dependencies are absent.
- **Docker 29 unhealthy-on-exit (#789, #790).** The e2e dead-service scenario uses a per-scenario
  startup check strategy so an intended exit before the first health probe is not misreported.
- **Nightly example templates carry a `repository` (#785, #786)** — night one's all-runs-die-at-setup
  failure mode, pinned by regression tests.
- **Owner-transfer API (#760, #780)**: `POST /api/runs/reassign` moves a removed bot's Runs to a new
  owner atomically before teardown. **`host bot status` (#759, #782)** clears partial view data when
  the API walk fails. The nightly blocking question rides on the issue body when the nightly identity
  owns it (#770, #778); the nightly skills share one helper module (#769, #779).

## The CLI

`mercuryctl`, the operator client, ships inside this same package — there is no separate CLI artifact
and no CLI-only channel. Both binaries arrive with any install:

```bash
mercuryctl --version        # 0.2.1
mercuryctl runs list --host http://127.0.0.1:3000
mercuryctl run <runId>      # timeline, events, workspace pointer
```

The CLI talks to the same owner-scoped API the dashboard uses, including the mutating commands
(`runs create`, `runs input`, `runs cancel`, `runs retry`, `runs goal-cancel`); every endpoint it calls
is documented in [`docs/api.md`](../../../docs/api.md).

## Upgrading

No breaking changes: the API schema version is unchanged, migrations are additive, and the bot config
format is backward compatible. Nightly hosts that rely on the ladder should re-read
`docs/nightly-self-development.md` §4.2 for the renumbered rungs. Operators running the nightly loop
should also restart their worker after upgrading — the zero-output guard lives in the worker's adapter.
