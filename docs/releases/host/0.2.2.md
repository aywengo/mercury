# Mercury host 0.2.2

Two weeks of nightly self-development plus four feature slices. The headline is **advisory Workflow
Templates**: a template can now be listed, validated, snapshotted onto a Run, rendered into the agent's
prompt, and shown against the steps the agent actually reports. Alongside it: a per-Run `model`,
credential profiles resolved per Run, Fleet per-host availability, and the Laya sidecar.

## Install

```bash
npm install -g @aywengo/mercury        # 0.2.2
```

Or:

```bash
git clone https://github.com/aywengo/mercury.git
cd mercury
npm ci
```

Or from Homebrew (formula `mercury-ai`; homebrew-core owns `mercury`, the Mercury language compiler):

```bash
brew tap aywengo/mercury https://github.com/aywengo/mercury
brew install mercury-ai
```

Requires Node.js >= 22.18 and `git`. `mercury --version` prints `mercury-host 0.2.2`; `GET /healthz`
reports `"version": "0.2.2"`.

## The headline: advisory Workflow Templates

A Workflow Template names a sequence of stages, each with its own preset, and Mercury renders it into
the agent's prompt as a plan. It is **advisory**: Mercury shows the plan and records what the agent
reports, and never claims to enforce the order. The three slices landed together.

**W-1 — the schema and registry (#812).** `src/workflows/` holds the template schema, structured
validation with stable `WORKFLOW_*` finding codes, and a registry over a shipped `workflows/<id>/`
directory, modelled on `PresetRegistry`: per-template error isolation, deterministic ordering,
symlink and containment refusals, and the same canonical content hash the preset registry uses. One
builtin ships — `plan-implement-review`: `system-architect` plans, the default agent implements,
`reviewer` reviews. `mode: staged` is refused by name; staged execution is Phase 9.

**W-2 — create one advisory Run from a template (#842).** `POST /api/runs` (and `RunService.create`)
accepts `workflow: { id, version? }`. Resolution:

- Required agents across stages must agree, or creation fails with `WORKFLOW_STAGE_AGENT_CONFLICT`;
  a non-required stage preference is ignored — caller beats system default.
- The same agreement rule applies to models (`WORKFLOW_STAGE_MODEL_CONFLICT`).
- Constraints fold to the **narrowest ceiling** across stages; `networkMode: none` beats `bridge`.
- Skills are the **union of the stages' required skills**; exceeding the cap fails and names the
  stages rather than dropping anything.

The creation transaction snapshots the template bytes, every template file, the canonical hash, the
resolved version, and one row per referenced preset (migration v14, `run_workflows`). A later edit to a
template or preset cannot change an existing Run: the worker renders from the snapshot, never the live
registry. `src/workflows/renderPlan.ts` renders deterministically — the same snapshot yields a
byte-equal plan — and the prompt states the step bound and labels the plan advisory.

**W-3 — the API and the dashboard view (#934).**

```
GET  /api/workflows                      # valid templates; ?includeInvalid=1 adds findings, admin-gated
GET  /api/workflows/:workflowId          # one template, its stages, the presets they reference
POST /api/workflows/:workflowId/runs     # create the advisory Run; workflowVersion pins the version
```

Template reads are host configuration and available to every authenticated caller (the `/api/presets`
rule); Run creation uses the authenticated owner. The dashboard gains a Workflows page and a
**planned steps** panel on the Run detail, listing the snapshot's steps next to the steps the agent
reported. The panel says **"agent-reported — not enforced by Mercury"**, and a planned step with no
reported event reads *not reported* — never *skipped* or *failed*, because Mercury does not know.

The `/api/workflow-runs/*` group endpoints are staged-mode and deliberately absent.

## A model per Run (#823, #832–#836, #849)

`POST /api/runs` ignored `body.model`. The only place a model could live was inside a preset snapshot,
so a non-preset Run could not take one at all. Now:

- `model` is validated in `create()` — non-empty, at most 200 characters, no whitespace or control
  characters — and resolved by one rule on both paths: `caller.model` → preset model → none.
- It is persisted on the `runs` row, carried through retry, and passed to every adapter. PrimeAgent
  and hermes emit `-m`; Claude honours `context.model`; Fleet passes it through to the child.
- A value that starts with `-` is refused (#849, #850). It reaches argv, so `-x` and
  `--dangerously-skip-permissions` were previously accepted. Real ids such as `claude-sonnet-4-5`,
  `zai/glm-5.3-flash` and `qwen3.8:32b` still pass.

Each adapter declares `perRunModel` only after the capability was measured, so a bot can filter on it
(#861).

## Credential profiles, resolved per Run (CP-3, #841)

`resolveProfile(profiles, ownerId, repositories)` decides **which** profile a Run uses and refuses Runs
that may not use it — the four outcomes of the design's §5.3: `none`, `profile <name>`, refused
`multiple-profiles`, refused `owner-not-allowed`. Repository ids come from `repository` plus every
entry of `repositories`; a `localPath`-only entry has no id and matches nothing, and owner comparison is
case-insensitive. Resolution runs before anything is written.

**No credential delivery yet** — environment and git delivery are CP-4. With no profile file present,
nothing observable changes.

## Fleet sees what a host can do (FB0, #978)

Fleet's prober now reads `GET /api/presets` and `GET /api/workflows` on the same sweep, with the same
credential and timeout, and caches one snapshot per host (Fleet migration v6). The failure semantics
are the point: a failed or partial read **keeps the previous snapshot and marks it stale**, and a
snapshot is never replaced with an empty list on error. Outcomes that never reached the host —
unreachable, timeout, not_mercury, incompatible, unauthorized — touch nothing, so "no new information"
cannot look like "no capabilities".

## The Laya sidecar (#825, #830, #831, #845)

`src/laya/` holds the wire contract (one `choice` question over opaque option keys, a redacted state
allowlist, and a stable failure vocabulary), a zero-dependency `node:http` client, and a scripted fake.
The host installer asks **`Install the Laya sidecar?` — default no**; opting out writes nothing at all.
Opting in gates on Python >= 3.10 (the macOS system 3.9.6 is refused with the reason), builds a
**versioned** venv pinned to `laya[serve]==0.3.25`, generates a 32-hex `LAYA_API_KEY` into the 0600
`bot-credentials.json` (a re-run preserves an existing key), and writes the service unit.

The unit is the only commit point: a failed install deletes the build directory and leaves the previous
unit and venv byte-identical, and a failed activation restores the previous unit bytes. Each install
keeps exactly one previous generation. `host doctor` gains a Laya probe line when `MERCURY_LAYA_URL` is
set (#830).

## Other changes

- **`runs.statusChangedAt` (B2-0, #959).** Migration v18 adds the column, and `RunStore.transition`
  writes it in the same `UPDATE` as the status it describes. Rows written before the migration serve
  `null`, never a fabricated time.
- **`selection` on `POST /api/runs` (L1-1, #865).** An optional record of Laya's pick and its
  distribution, validated fail-closed (allowlisted keys, at most 8 KiB, finite probabilities in
  `[0, 1]`). `chosen` must equal the Run's effective `agent` and `model` in both directions, so the
  record can never misreport what ran. It is exposed as `selection` on the Run detail.
- **Dispatcher bot selection (L1-2, L1-3; #861, #866).** A pure candidate hard filter — agents absent
  from `GET /api/agents`, models whose agent lacks `static.perRunModel`, and malformed model values are
  dropped with indexes and reasons — and the §6.3 question / §6.4 decision rule, where 0 candidates
  throws, 1 candidate is chosen without a call, and a sidecar failure is distinguished from an invalid
  response.
- **A misspelled preset version pin is refused (#859, #935).** `body.preset` was forwarded unresolved
  and read only for `id`/`version`, so `versoin` was silently dropped and resolved the *current* preset
  — the typo-and-downgrade case the pin exists to catch. The block is now shape-validated at the same
  choke point as the workflow block, with a did-you-mean hint.
- **Nightly worktree state cannot be committed (#942, #943).** `.mercury-sessions/` and
  `session-artifacts/` are now excluded, so a bulk `git add -A` cannot commit agent session transcripts
  or kernel-state snapshots. One of those snapshots had contained the revoked `GH_TOKEN`.
- **Host setup hardening (#851, #862).** The launchd not-loaded check is built from the actual unit
  label instead of a hard-coded one, and a `.laya-venv-prev` marker is trusted only inside installer
  data dirs.
- **Bot task-level `select` (#826, #838)** is accepted, shape-validated, and reserved against
  collisions.

## The CLI

`mercuryctl`, the operator client, ships inside this same package — there is no separate CLI artifact
and no CLI-only channel. Both binaries arrive with any install:

```bash
mercuryctl --version        # 0.2.2
mercuryctl runs list --host http://127.0.0.1:3000
mercuryctl run <runId>      # timeline, events, workspace pointer
```

The CLI talks to the same owner-scoped API the dashboard uses, including the mutating commands
(`runs create`, `runs input`, `runs cancel`, `runs retry`, `runs goal-cancel`); every endpoint it calls
is documented in [`docs/api.md`](../../api.md).

## Upgrading

No breaking changes. The API schema version stays at **1** — everything added here is additive, so an
older Fleet keeps working against this host, and `MIN_HOST_API` is unchanged. Migrations are additive
(v14 `run_workflows`, v18 `runs.status_changed_at`; Fleet v6 `host_availability`). The bot config format
is backward compatible.

Two operator notes:

- The workflow features are **advisory only**. Nothing schedules child Runs, and no endpoint enforces
  stage order; a Run created from a template is one ordinary Run whose prompt carries a plan.
- `MERCURY_LAYA_URL` unset means no Laya at all — no question is asked, no sidecar is probed, and the
  dispatcher falls back to a literal template.
