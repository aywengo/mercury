# Mercury host 0.2.3

A short release covering everything merged after 0.2.2. Three host-side changes matter to an operator:
the **A2A binding** is now mounted, a local Run's **environment is built in layers** from credential
profiles instead of inheriting the worker's, and **secrets are redacted from agent artifacts at rest**.
The nightly loop also stops letting a Run end silently: it records unpushed commits, and it reports
Runs that never called their exit path.

## Install

```bash
npm install -g @aywengo/mercury        # 0.2.3
```

Or:

```bash
git clone https://github.com/aywengo/mercury.git
cd mercury
npm ci
```

Or from Homebrew (formula `mercury-ai`; homebrew-core owns `mercury`, the Mercury language compiler):

```bash
brew tap aywengo/mercury https://github.com/aywengo/mercury
brew install mercury-ai
```

Requires Node.js >= 22.18 and `git`. `mercury --version` prints `mercury-host 0.2.3`; `GET /healthz`
reports `"version": "0.2.3"`.

## A2A binding (A0-1..A0-4, #995, #996, #998, #1000)

`@a2a-js/sdk` is pinned at `1.3.0` and its REST binding is mounted on Mercury's server from `src/a2a/`.
The mapping from a Run to an A2A task state is exhaustive over `RunStatus`, so a new status cannot
fall through to a default. A Run carries a server-only origin that the binding filters by, and a retry
links its predecessor inside the insert transaction, so the retry intent survives a crash instead of
leaving two unrelated Runs.

The binding is off unless configured: with no `MERCURY_A2A_*` setting the server mounts nothing and
behaves exactly as it did in 0.2.2.

## A local Run's environment is built in layers (CP-4, #977)

`src/worker/runEnvironment.ts` replaces "hand the agent the worker's `process.env`" with the four
layers of the credential-profiles design: the stripped base environment, the profile's own values, the
per-Run overrides, and the caller's additions. A profile gets an isolated `GH_CONFIG_DIR` and a
generated gitconfig, so two Runs with different GitHub identities cannot see each other's credentials.

A `file:` credential source that is missing at drive time **fails the Run** with the design's message.
It never falls back to the worker's environment and never to an empty value.

## Agent artifacts are redacted at rest (#944, #965)

The event store already redacted payloads. The agent's own artifacts in the workspace did not: session
transcripts under `.mercury-sessions/*.jsonl` and the other agent-state directories were kept exactly
as written. The worker now rewrites those files through the same redactor before the workspace is
retained, so a transcript that echoed a token no longer keeps it on disk.

## Unpushed commits are recorded, not inferred (#1024, #1025)

A Run that commits and stops used to look like a success with no PR. On COMPLETED the worker now
compares the workspace's `HEAD` with its **remote-tracking refs**, scoped to the Run's own
`baseCommit..HEAD`, and records the branch and the commits that were never pushed as
`run.unpushed_commits`. The Run detail shows an `unpushed N` badge.

Two limits are deliberate. The finalize path never fetches — a push from the worktree already updates
its own remote-tracking ref, and a fetch would bound finalization by remote latency — so a push made
by URL reads as unpushed, which is the safe direction. And a workspace with no remote refs at all
reports nothing, so a local fixture or a copy-mode Run is never flagged.

The nightly digest gained two sections built on it: **Runs that ended with unpushed commits** and
**nightly Runs that never called finish/blocked**, both naming the Run and its worktree. The digest
also always states the host version and the loaded `issue-fix-loop` version, and warns when the loaded
copy is older than `main` — the failure that made a nightly host run a stale skill for weeks (#1023).

## The CLI

`mercuryctl`, the operator client, ships inside this same package — there is no separate CLI artifact
and no CLI-only channel. Both binaries arrive with any install:

```bash
mercuryctl --version                    # 0.2.3
mercuryctl runs show <runId>            # timeline, events, workspace pointer
```

The CLI talks to the same owner-scoped API the dashboard uses; every endpoint it calls is documented
in [`docs/api.md`](../../api.md).

## Upgrading

No breaking changes. The API schema version stays at **1** — everything added here is additive, so an
older Fleet keeps working against this host, and `MIN_HOST_API` is unchanged. Migrations are additive.
The bot config format is backward compatible.

Two operator notes:

- **Reinstall or upgrade the skills with the package.** The nightly loop reads its skills from the
  installed package, so a host that keeps an old `node_modules` keeps running the old skill. After
  upgrading, `mercury host doctor` reports the loaded skill version, and the nightly digest now warns
  when it is behind `main`.
- **`run.unpushed_commits` is advisory.** Mercury records what it saw at finalize time; it does not
  push, and it does not retry.
