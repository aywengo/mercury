# Mercury host 0.2.7

A patch release that lets a fresh host actually execute a Run. 0.2.6 made `mercury host service
install` write the worker service; on a clean host the worker then found no harness — neither a
systemd user unit nor a launchd agent inherits `~/.local/bin` — and the npm install path had no data
directory to open. Both are fixed here.

## Install

```bash
npm install -g @aywengo/mercury        # 0.2.7
```

Or:

```bash
git clone https://github.com/aywengo/mercury.git
cd mercury
npm ci
```

Or from Homebrew (formula `mercury-ai`; homebrew-core owns `mercury`, the Mercury language compiler):

```bash
brew tap aywengo/mercury https://github.com/aywengo/mercury
brew install mercury-ai
```

Requires Node.js >= 22.18 and `git`. `mercury --version` prints `mercury-host 0.2.7`; `GET /healthz`
reports `"version": "0.2.7"`.

## The service units put the user's bin on PATH (#1074, PR #1075)

`prime-agent` installs itself to `~/.local/bin`, and `mercury host setup` probes and finds it
(`harnesses: primeagent`). But a systemd user unit's default PATH is
`/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin`, and a launchd agent inherits a minimal PATH too,
so the worker spawned `prime-agent`, got ENOENT, and every Run failed at once:

```
"error":"Agent exited with code 127 (signal none)","errorKind":"agent","status":"FAILED"
```

Both units now carry an explicit `Environment=PATH=` — the resolved `mercury` binary's directory,
`~/.local/bin`, then the system defaults — and both launchd wrappers export the same prefix before
exec. On a fresh Debian 13 container with systemd user units this is the difference between

```
smoke primeagent: FAIL - primeagent smoke run run_3866d473dd7441b0 FAILED
```

and

```
smoke primeagent: PASS - primeagent smoke run run_c86b774630de4f1f completed
```

## Opening the database creates its directory (#1074, PR #1075)

`mercury host setup` prints `data dir: ~/.local/state/mercury` and did not create it. `mercury
server` and `mercury worker` then failed with `ERR_SQLITE_ERROR: unable to open database file`, and
systemd restarted both forever. The `curl | bash` installer hid this by writing
`install.log` into that directory first; the `npm install -g` path documented above has no such side
effect. `openDatabase` now creates the parent directory, the way the CLI already creates the
workspace base.

**Upgrading a host installed before 0.2.6:** `mercury host upgrade` restarts the host service only.
Re-run `mercury host service install` afterwards so the worker service exists.

## The CLI

`mercuryctl`, the operator client, ships inside this same package — there is no separate CLI artifact
and no separate version to track:

```bash
mercuryctl --version                    # 0.2.7
mercuryctl runs show <runId>            # timeline, events, workspace pointer
```

The CLI talks to the same owner-scoped API the dashboard uses; every endpoint it calls is documented
in [`docs/api.md`](../../api.md).
